# 评估标准：什么是一份出色的业务上下文共识文档？

一本优秀的 `context.md` 是项目业务知识的中枢和免疫系统。它使 Agent 在没有人实时把关、不记得上一个会话发生了什么的时候，依然能“有据可查”，避开非目标领域，维持业务术语的高度一致。

---

## 合格度自检标准（及格线）
生成的 [context.md](context.md) 必须全盘通过以下 6 项核心指标，任意一项不合格均被视为低质量交付：

- [ ] **1. 一句话定位不失真 (Context Precision)**
  - 核心愿景和一句话定位必须能让完全不了解此项目的 Agent 在 3 秒内抓准调性。
  - 示例：“这是一款针对非技术人员的自建知识库检索面板，核心瓶颈在交互简单性而非高并发吞吐。”

- [ ] **2. 明确的“非目标/排除范围” (Scope Defensiveness)**
  - 必须写明任何“当前不应做、目前不需要、已明确被排除在外”的功能或复杂功能设计。
  - 原因：LLM 惯于提出宏大、完美但累赘的技术方案扩展，明确的排除范围防线（Non-Goals）能极大阻击无意义的代码膨胀与开发成本。

- [ ] **3. 专有名词表无多义性 (Zero-Ambiguity Dictionary)**
  - 只要对话中用户提出了自主命名的机制、表名、服务，必须记录在 Glossray 中。
  - 理由：防止 Agent 后续生造意义相同但英文命名不同的新名词（例如将 `UserConsensus` 和 `UserAgreement` 混用）。

- [ ] **4. 记录决策背后的权衡 (Architectural Trade-offs)**
  - 任何技术方案或业务路径一经用户拍板，不但要记录最终选择，还要用一两句话记下“为什么否定了另一选项”。
  - 理由：防止后续新介入的 Agent 在不了解历史的情况下，又重新建议那个已被用户否决或被历史证明不可行的老路子。

- [ ] **5. 历史可追溯性 (Incremental & Logged)**
  - 文档底部必须包含 `变更日志 (Maintenance History)`段落。
  - 每次执行该技能修改 [context.md](context.md)，都必须按日期规范（形如：`[YYYY-MM-DD]`）在末尾进行日志滚动追加。

- [ ] **6. 绝对客观，杜绝抒情与空话 (No Bullet Point without Substance)**
  - 严禁空洞模版语调，文档应全部由经过审查核实的事实、名词、决策、明确指令和具体的非目标构成。
  - 清单不能全是 placeholders（大括号插值）。只要是最终交付，插值必须被切实的用户数据完全填满。

## 负面清单：什么是一份糟糕的共识文档？
- ❌ **整篇假大空**: 只有大纲，里面的实际内容都是 “{请输入你的具体背景}” 却从未落实，导致其实质上仍是一个不可使用的空架子。
- ❌ **缺乏 Non-Goals**: 遇到什么奇特的技术扩展都打算往项目里硬塞，缺失防护圈。
- ❌ **单次对话重写**: 每次对齐都把旧的历史决策一锅端清除，让 Agent 对过去几个星期的设计缘由彻底眼盲。
