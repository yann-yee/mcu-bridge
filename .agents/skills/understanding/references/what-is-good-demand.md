# What Makes a Good Goal Model?

一份优秀的需求文档不是“细节最多”，而是能让后续 Agent 在实现发生变化时仍然守住正确目标。

## 质量标准

- [ ] **Project Alignment 清楚**：能说明本需求如何服务项目长期目标或当前战略目标；若未知则明确标记，而不是编造价值。
- [ ] **问题与方案分离**：先描述 Current State / Observed Problem，再描述 Desired Outcome；“加按钮”“新增类”不能替代问题定义。
- [ ] **Desired Outcome 可判断**：完成后系统或用户状态可以被客观观察，而不是“更优雅”“更好用”。
- [ ] **What Good Looks Like 有取舍**：只选择相关质量维度，并写出能指导工程决策的标准。
- [ ] **策略不越级到函数级**：可以确认架构方向，但除非属于外部兼容契约，不冻结类名、函数签名和修改文件清单。
- [ ] **事实与假设可区分**：高影响 unknown 不允许悄悄变成 requirement。
- [ ] **Non-Goals 明确**：防止 Agent 在局部实现中扩大范围。
- [ ] **Acceptance Evidence 定义“证明什么”**：不要在尚未调查代码前杜撰测试文件和命令。
- [ ] **简洁但足够决策**：一个零上下文 Agent 阅读后，能够判断某个局部实现选择是否推动目标、是否破坏边界。

## 反模式

### 细节很多但没有目标

```text
新增 A 函数
新增 B API
新增 C 页面
```

却没有说明系统为什么需要这些东西。

### 把方案误写成需求

```text
必须使用 Toast 提示成功
```

真正不变量可能只是：

```text
用户必须无需跳转即可明确知道操作是否成功。
```

### 为完整而穷举边缘条件

需求文档不是威胁模型百科。只记录会改变目标、业务规则、恢复语义或验收方式的关键场景；实现层面的普通防御由项目规则、code-spec 与执行阶段处理。

### 假装知道代码现实

没有证据时不要写：

```text
修改 src/foo.c::foo_init()
```

这属于 `code-spec` 的证据调查范围。

## 最终检查问题

读完文档后，后续 Agent 应该能够回答：

1. 为什么值得做？
2. 现在的问题到底是什么？
3. 完成后什么状态必须发生变化？
4. 什么质量特征决定“做得好”？
5. 哪些东西不能顺手改掉？
6. 当前还有什么高影响未知？

如果这些问题答不出来，即使文档有很多用例和字段，也不是合格的 Goal Model。
