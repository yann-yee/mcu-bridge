## 1. 背景与动机

在 AI Agent 普及的当下，Agent 已经可以完成嵌入式程序的编写与烧录，但存在三个痛点：

1. **编译烧录命令碎片化**：不同 debugger、芯片、接口的组合导致 OpenOCD 命令差异大，Agent 需要多次试错才能得到正确命令，严重浪费 token。
2. **Agent 与 MCU 的时钟错配**：Agent 的思考耗时（秒级到分钟级）与 MCU 的实时执行（微秒级）存在巨大鸿沟。Agent 还没分析完当前断点数据时，MCU 已经把关键逻辑跑过去了，传统调试模式（暂停→看数据→继续）对 Agent 不适用。
3. **交互通道割裂**：调试靠 GDB/OpenOCD，串口日志靠另一个终端，Agent 需要同时协调多个通道，上下文切换成本高。

### 核心洞察

**用缓冲区解耦 Agent 的慢思考与 MCU 的快执行。**

思路借鉴逻辑分析仪：不在断点处停下等使用者，而是持续采集、带时间戳存储，让 Agent 事后翻阅调试历史记录。同时统一调试器与日志通道两条数据流，一个入口交予 Agent。

## 2. 技术栈

| 层面 | 选择 | 理由 |
|------|------|------|
| 语言 | Rust | 零成本抽象、trait 天然适合多后端、编译为单一二进制无运行时依赖 |
| 调试后端（默认） | probe-rs | 纯 Rust 嵌入式调试方案，API 驱动无需外部进程 |
| 调试后端（兜底） | OpenOCD | 覆盖 probe-rs 不支持的非主流芯片 |
| 日志通道 | RTT / UART / Semihosting | RTT 优先，UART 次之，Semihosting 兜底 |
| 对外接口 | CLI + 结构化 JSON | Human REPL 模式 + Agent JSON-Lines 模式 |
| 缓存目录 | `~/.mcu_bridge/` | 会话级缓存，正常退出自动清理 |

**工具名称**：`mcu-bridge`

Session 管理协调三层子系统：
- **DebugProbe（3.1）** — 对调试探针的抽象，提供烧录/断点/内存/寄存器操作
- **DebugBuffer（3.2）** — 定时采样 + 断点快照 → ring buffer，Agent 的事后翻阅入口
- **LogChannel（3.3）** — MCU ↔ 主机文本流，RTT/UART/Semihosting 统一抽象

### 3.1 调试探针层 (DebugProbe)

#### Trait 定义

```rust
trait DebugProbe {
    // 会话
    fn attach(&mut self, chip: &ChipConfig) -> Result<()>;
    fn detach(&mut self) -> Result<()>;

    // 连接自恢复
    fn is_connected(&self) -> bool;
    fn try_recover(&mut self) -> Result<()>;

    // 烧录
    fn flash(&mut self, elf: &Path, opts: &FlashOpts) -> Result<()>;

    // 执行控制
    fn halt(&mut self, core: Option<usize>) -> Result<()>;
    fn resume(&mut self, core: Option<usize>) -> Result<()>;
    fn step(&mut self, core: Option<usize>) -> Result<()>;

    // 多核
    fn core_count(&self) -> usize;
    fn active_core(&self) -> usize;

    // 断点
    fn set_breakpoint(&mut self, addr: u32, core: Option<usize>) -> Result<BpId>;
    fn clear_breakpoint(&mut self, id: BpId) -> Result<()>;

    // 数据观测
    fn set_watchpoint(&mut self, addr: u32, len: u32, kind: WatchKind) -> Result<WpId>;
    fn clear_watchpoint(&mut self, id: WpId) -> Result<()>;

    // 内存与寄存器
    fn read_mem(&mut self, addr: u32, len: u32, core: Option<usize>) -> Result<Vec<u8>>;
    fn write_mem(&mut self, addr: u32, data: &[u8], core: Option<usize>) -> Result<()>;
    fn read_regs(&mut self, core: Option<usize>) -> Result<HashMap<String, u64>>;

    // 状态
    fn is_halted(&self, core: Option<usize>) -> bool;
}
```

上层（Session / DebugBuffer / LogChannel / CLI）只依赖这个 trait，完全不感知底层是 probe-rs 还是 OpenOCD。

#### probe-rs Backend（默认）

- 通过 `probe-rs` crate 直接驱动调试探针（CMSIS-DAP / J-Link / ST-Link 等）
- 无需外部进程，纯 API 调用
- 解析 ELF 的 DWARF 调试信息，支持按函数名、文件名:行号设置断点
- 支持读取 C 变量（全局变量、static 变量）的地址与值
- 芯片支持：主流 Cortex-M（STM32、nRF、RP2040、LPC、Kinetis、ATSAM 等）

#### OpenOCD Backend（兜底）

- 启动 OpenOCD 子进程，通过 `localhost:6666` 的 TCL telnet 接口通信
- 适配 probe-rs 不支持的非主流芯片（冷门 Cortex-M、RISC-V、Xtensa 等）
- 用户可指定自定义 OpenOCD 配置文件

**TCL 通信策略**：

TCL 命令是同步的——发完等返回即可，不轮询验证。区分两类场景：

| 场景 | 做法 | 原理 |
|------|------|------|
| 同步命令（halt、resume、bp、mdw、reg） | 解析返回中的 `OK` / `ERROR` | 命令执行完才返回提示符 |
| 异步事件（断点命中、目标 halted） | 接收线程监听 telnet socket，关键词列表匹配 | OpenOCD 主动推送消息 |

关键词列表：`["halted", "breakpoint", "target halted", "target state: halted"]`。匹配任何一个即视为命中。版本差异靠扩充列表解决，不做结构化解析。

TCL 命令超时（默认 5s）视为后端异常。不重试单条命令——超时意味着 OpenOCD 进程状态混乱，此时杀掉子进程 → 重启 → 重新 attach。

**版本策略**：以 OpenOCD 0.12 为基准。关键词匹配天然容错版本差异，不做多版本兼容矩阵。CI 中维护固化 openocd 版本的 docker 镜像用于集成测试。

#### Backend 选择逻辑

1. 若芯片在 probe-rs 支持列表中 → probe-rs
2. 若用户显式指定 `--backend openocd` 或提供了自定义 cfg → OpenOCD
3. 配置文件兜底

#### 探针连接自恢复

策略：
1. 每次操作前通过 `is_connected()` 检查连接状态
2. 失联时自动调用 `try_recover()` 尝试重连（probe-rs 有内置的 probe 重枚举能力）
3. 重连成功后自动恢复之前的断点/watchpoint 设置
4. 连续重试 N 次（默认 3 次）仍失败 → 会话优雅退出，保留已采集的缓冲区数据
5. 恢复期间的采样数据标记 `gap = true`

#### 多核支持

委托给 probe-rs 的多核能力（`Session` / `Core` 模型原生支持 Cortex-M4 + M0 等异构架构）。

- `DebugProbe` trait 的 core 参数默认为 `None`（活跃核），显式传 `Some(n)` 指定目标核
- `core_count()` 返回探针检测到的核数
- 各核的断点和 watchpoint 独立管理，DebugBuffer 记录中 `core` 字段区分来源
- 不支持多核的芯片降级为单核模式并给出警告

**采样线程模型**：单线程轮询所有核。多核共享同一根 SWD 总线，物理上就是串行化的——拆多线程只会增加 probe-rs Session 内部的 Mutex 竞争，没有收益。典型 M4 + M0 异构场景各核 4 个 watch，一轮约 640μs，对 10ms 周期可忽略。

```rust
fn sample_round(session: &mut Session, watches: &[WatchTarget]) {
    let tick = now_us();
    for core in 0..session.core_count() {
        for watch in watches.iter().filter(|w| w.core == core) {
            let val = session.read_mem(watch.addr, watch.size, Some(core));
            buffer[core].push(Sample { tick, val, core, .. });
        }
    }
}
```

### 3.2 调试缓冲层 (DebugBuffer)

核心差异化能力。Agent 不与实时 MCU 交互，与缓冲的历史数据交互。

#### 数据结构

```
每个 Watch Target 一个 ring buffer:

┌────────────────────────────────────────────────────────────────┐
│ [sn=1]    [sn=2]    ...  [sn=99]    [sn=100]                   │  ← 最多 N 条
│  val=42    val=42           val=99     val=100                 │
│  bp_flag=true               bp_flag=false                      │
│  core=0    core=0           core=0     core=1                  │
│  gap=true  gap=false        gap=false  gap=false               │
│  tick=1234 tick=1235        tick=...   tick=...                │  ← μs 时间戳
│  regs={...}                                                     │  ← 寄存器快照 (仅 bp_flag=true)
└────────────────────────────────────────────────────────────────┘

全局序列号递增，Agent 增量查询 (buffer --since N)
```

#### 采集机制

- **定时采样为主**：`continue` 后每隔 `watch.interval_ms`（默认 10ms）由独立线程触发一轮采样，遍历所有 watch target 读当前值写入 ring buffer。不依赖 MCU 侧 timer 外设。
- **断点触发时额外采样**：断点命中时强制执行一轮采样，附带该核的完整寄存器快照（`bp_flag = true`）。Agent 翻阅 buffer 时能明确看到"MCU 在这里停过"。
- **watchpoint 触发时采样**：硬件 watchpoint 命中时采样，写 watch 记录 `old_val` / `new_val` 变化。
- **连接恢复标记**：探针断连期间无法采样，恢复后第一条记录 `gap = true`。

每个 watch target 独立 ring buffer，默认容量 128 条（可配置）。写满后覆盖最旧记录。

#### SWD 采样开销

采样不需要 halt MCU——Cortex-M 调试接口支持在 CPU 运行中通过 SWD 读内存。

- 单次 32-bit SWD 内存读取约 **50-80μs**（4MHz 时钟下 8 个帧周期 + 协议开销）
- 8 个 watch target 一轮全量采样约 **400-640μs**
- 10ms 周期下占用率仅 **4%-6.4%**，100ms 周期则 **<1%**

结论：默认 10ms 安全可行，硬实时场景允许用户调大到 100ms 或更大。

#### 全局寄存器快照

每次 `bp_flag = true` 时额外记录所有 core registers 的完整快照。Agent 可在断点间回溯调用栈。

### 3.3 日志通道层 (LogChannel)

UART、RTT、Semihosting 统一抽象——都是 MCU ↔ 主机的文本字节流。

```rust
trait LogChannel: Send {
    fn name(&self) -> &str;            // "rtt" | "uart" | "semihosting"
    fn open(&mut self) -> Result<()>;
    fn read(&mut self, buf: &mut [u8]) -> Result<usize>;
    fn write(&mut self, data: &[u8]) -> Result<()>;
    fn is_writable(&self) -> bool;
    fn close(&mut self) -> Result<()>;
}
```

#### 三种实现

| | RttChannel | UartChannel | SemihostingChannel |
|---|---|---|---|
| 数据来源 | SWD 读 RAM ring buffer | 物理 UART 串口 | SWD 捕获 BKPT 异常 |
| MCU 开销 | 极低（纯内存写入） | 低（DMA 下零开销） | 高（每次 ~1-2ms，CPU halt） |
| 双向 | 是 | 是 | 否 |
| 适用场景 | **首选通道** | 引出 UART 且无 RTT 固件 | 无物理串口且无 RTT 固件 |

#### RTT（一等公民，首选通道）

**原理**：MCU 固件在 RAM 中维护 SEGGER RTT Control Block（含多通道 ring buffer 的地址和状态），调试器通过 SWD/JTAG 直接读取——不需要断点、不需要异常陷入、不需要额外引脚。

**优势**：MCU 侧只做 memcpy；SWD 轮询可达 MHz 级吞吐；双向通信；最多 16 通道；probe-rs 已有完整 RTT 支持，`RttChannel` 是薄封装。

**固件要求**：目标固件需链接 `SEGGER_RTT.c` / `SEGGER_RTT.h`（~500 行 C，BSD 许可），初始化时调用 `SEGGER_RTT_Init()`。任何支持 SWD 内存访问的探针都能用，不绑定特定硬件。

**检测策略**：启动时在目标 RAM 中搜索 RTT Control Block 的特征签名（`"SEGGER RTT"` 魔数）。Channel 0 为默认终端通道。

#### 通道选择

```
serial.backend = "rtt"         → 仅用 RTT，检测不到则报错
serial.backend = "uart"        → 仅用 UART，找不到端口则报错
serial.backend = "semihosting" → 仅用 Semihosting
serial.backend = "auto"        → RTT → UART → Semihosting 依次尝试
```

`auto` 模式的 fallback 链：

```
1. 搜索 RTT Control Block → 找到 → RttChannel
2. 未找到 → UART auto-detect → 找到 → UartChannel
3. 未找到 → 启用 Semihosting → SemihostingChannel
4. 全部失败 → 报错退出
```

#### 通道性能对比

| | RTT | UART (115200 DMA) | Semihosting |
|---|---|---|---|
| MCU 侧开销 | memcpy, <1μs/字符 | DMA, CPU 零开销 | BKPT, ~1-2ms/次 |
| 吞吐上限 | MHz 级 | ~11.5 KB/s | <1 KB/s |
| 额外硬件 | 无 | UART 引脚 + 串口线 | 无 |
| 固件改动 | 链接 SEGGER_RTT.c | 无 | 无（标准库内置） |
| 干扰实时性 | 几乎为零 | 零 | 严重（每次输出 halt CPU） |

#### Semihosting 降级说明

性能差是协议固有缺陷，不做优化。Semihosting 事件触发时暂停定时采样，避免与 `BKPT` 陷入竞争 SWD 总线。

#### SerialMonitor

独立线程，生命周期与 debug session 绑定，持有一个 `Box<dyn LogChannel>`。

```
┌───────────────────────────────────┐
│          SerialMonitor            │
│  ┌─────────────────────────────┐  │
│  │  接收线程                    │  │  持续从 LogChannel 读取
│  │  → Ring Buffer (文本)       │  │  带 μs 时间戳 + channel 来源标记
│  └────────┬────────────────────┘  │
│           │                       │
│  ┌────────▼────────────────────┐  │
│  │  write 通道                 │  │  Agent 可写命令给 MCU
│  │  (CLI / Agent 触发)         │  │  Semihosting 只读不可写
│  └─────────────────────────────┘  │
└───────────────────────────────────┘
```

- 自动检测：`auto` 按 RTT → UART → Semihosting 顺序
- 手动指定：`mcu-bridge init` 时配好 `serial.backend`
- 缓冲区与 DebugBuffer 共享时间基准，Agent 可跨通道对齐时间线
- `channel` 字段在多通道场景下区分日志来源

### 4.2 debug 会话

#### Session 生命周期（状态机）

```
                     ┌──────────┐
                     │  启动     │ parse config → select backend → attach probe
                     └────┬─────┘
                          │
                     ┌────▼─────┐
                     │  HALTED  │◄────────────────┐
                     │ (初始态)  │                  │
                     └────┬─────┘                  │
                          │                        │
          ┌───────────────┼───────────────┐        │
          │               │               │        │
     >continue        >step           >halt     (断点命中)
          │               │               │        │
     ┌────▼───┐     ┌───▼────┐          │        │
     │RUNNING │     │HALTED  │          │        │
     └───┬────┘     └────────┘          │        │
         │                              │        │
         │ 断点/watchpoint命中          │        │
         └──────────────────────────────┘        │
                                                 │
                     ┌──────────┐                 │
                     │RECOVERING│──重连成功───────┘
                     │(探针断连) │──重连失败──► EXIT
                     └──────────┘
```

初始状态为 **halted**，不自动 continue——让用户/Agent 先设断点和 watch。

#### 双模式

| | Human REPL | Agent JSON-Lines |
|---|---|---|
| 启动 | `mcu-bridge debug --elf fw.elf` | `mcu-bridge debug --elf fw.elf --json` |
| 界面 | 交互式 `> ` 提示符，有颜色 | 无提示符，stdin→JSON，stdout→JSON |
| 错误处理 | 彩色文本 | `{"status":"error","message":"..."}` |
| buffer 输出 | 折叠前 10 条 + `... (N more)` | 完整 JSON |
| 退出 | `exit` / `quit` / `Ctrl+D` | `{"cmd":"exit"}` |

#### 启动参数

```bash
mcu-bridge debug \
  --elf target/firmware.elf          # ELF 文件路径
  --config .debugger/chip.toml       # 配置文件（默认自动查找）
  --json                             # Agent JSON-Lines 模式
  --no-flash                         # 跳过烧录
  --verify                           # 烧录后校验
  --backend probe-rs                 # 强制指定后端
  --enable-flash-bp                  # 启用 Flash 断点
  --break main                       # 启动后立即设断点（可重复）
  --watch "sensor_data.temp,4"       # 启动后立即设 watch（可重复）
  --continue                         # 启动后立即 continue
  --halt-on-start                    # 无条件在 reset vector 处 halt
  --sampling-interval 100            # 覆盖采样间隔(ms)
  --serial-port /dev/ttyUSB0         # 覆盖串口端口
```

#### 命令全集

```
=== 会话控制 ===
  attach                     连接到探针 + 目标（debug 启动时自动执行）
  detach / exit / quit       断开连接，退出会话

=== 执行控制 ===
  continue [--core N]        全速运行
  halt [--core N]            暂停目标
  step [--core N]            单步（源码行级，需 DWARF）
  stepi [--core N]           单步（指令级）
  reset [--halt]             复位 MCU，--halt 在复位后保持 halt

=== 断点 ===
  break <target> [--core N] [--flash]
     target: main | src/sensor.c:142 | 0x08000420
     --flash: Flash 断点（需全局 --enable-flash-bp）
  clear <id> | clear all
  list-bp                    列出断点（id, addr, kind, core, 命中次数）

=== 数据观测 ===
  watch <target> <size> [--rw] [--ro] [--wo]
     target: sensor_data.temperature | 0x20001000
     size: 1 | 2 | 4 | 8
     --rw: 读写（默认）  --ro: 仅读  --wo: 仅写
  clear-watch <id> | clear-watch all
  list-watch                 列出 watch（id, label, addr, size, kind, buffer 填充量）

=== 缓冲区 ===
  buffer [--since N] [--watch <id>] [--last N]
     --since N:  从序列号 N 开始
     --watch id: 仅导出指定 watch
     --last N:   仅导出最近 N 条（human 模式默认 10）
  buffer-clear               清空所有 buffer

=== 日志通道 ===
  serial read [--since N] [--last N]
  serial write "<data>"      注意：semihosting 模式不可写
  serial clear               清空串口 buffer

=== 状态查询 ===
  status                     快速状态（halted/running, PC, 断点数, buffer 填充量）
  info                       芯片/探针/多核/所有断点watch/buffer 统计
  regs [--core N]            当前寄存器值（需 halted）
  history                    本次会话执行过的命令

=== 帮助 ===
  help                       列出所有命令（分组 + 一句话描述）
```

#### 命令可用性矩阵

| 命令 | HALTED | RUNNING | RECOVERING |
|------|--------|---------|------------|
| `continue` | OK | error: already running | error |
| `halt` | warn: already halted | OK | error |
| `step` / `stepi` | OK | error: not halted | error |
| `reset` | OK | OK | error |
| `break` / `clear` / `watch` / `clear-watch` | OK | OK | error |
| `buffer` / `serial read` | OK | OK | OK |
| `regs` | OK | error: target not halted | error |
| `detach` / `exit` | OK | OK (自动 halt) | OK |

## 7. Flash 断点

硬件断点 4-6 个的限制对 Agent 调试是瓶颈。Flash 断点用 BKPT 指令替换 Flash 中的指令可突破此限制，但代价明确：

- **慢**：每次设置/清除涉及 Flash 扇区擦写（几十到几百 ms）
- **耗寿命**：频繁操作消耗 Flash 擦写次数（通常 10K-100K 次）
- **XIP 不可用**：代码在外部 QSPI Flash 上执行时无法使用

设计决策：

- 默认关闭，需 `--enable-flash-bp` 显式开启
- 复用 probe-rs 的 Flash 断点 API
- 每会话设置总次数硬上限（默认 100 次）
- 设置时 CLI 输出警告；buffer 中 `bp_kind` 字段区分 `"hw"` / `"flash"`
- 实现优先级：P3

## 8. 缓存管理

缓存目录 `~/.mcu_bridge/`，按项目（目录 hash）和会话时间戳组织：

```
~/.mcu_bridge/
├── <project_hash>/
│   ├── 20260602T143052Z/    ← 单次调试会话
│   │   ├── session.json     ← 断点/watch 配置 + buffer 快照
│   │   └── serial.log       ← 日志通道原始输出
│   └── 20260602T150000Z/
└── chip_templates/           ← 用户自定义芯片模板
```

- 会话正常退出（`halt` → `detach`）→ 自动删除当次缓存
- 异常退出（crash / 断连恢复失败）→ 保留缓存，便于事后排查
- 每次启动时检查总大小，超过阈值（默认 512MB）按最旧优先清除

```bash
mcu-bridge clean                 # 清理当前项目
mcu-bridge clean --all           # 清理所有项目
mcu-bridge clean --older-than 7d # 清理 N 天前的缓存
```
